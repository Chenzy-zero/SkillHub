# 企业内部 Skill 安全管理方案

> 文档版本：V1.0
>
> 文档状态：正式方案
>
> 适用对象：公司内部 Skill 的开发、维护、审查、上架、使用和退役
>
> 生效日期：2026-08-27

本文件只说明公司内部 Skill 的统一管理规则和正式流程，不包含建设计划、工具实施顺序和历史方案。具体建设安排见 `docs/12-skill-security-implementation-plan.md`。

## 1. 方案目标

本方案用于建立公司内部 Skill 的统一安全管理机制，让每个正式使用的 Skill 都能做到：

- 知道来自哪个代码仓库、哪个目录和哪个版本；
- 知道由哪个产品线和负责人维护；
- 内容发生变化时能够及时发现；
- 上架前经过自动检查和必要的人工审查；
- 只有审查通过的明确版本才能进入公司 SkillHub；
- 上架后能够持续关注风险，并在必要时下架；
- 从发现、审查、上架到退役都有记录可查。

## 2. 管理范围

本方案管理以下 Skill：

- 已经进入公司 Gerrit 代码仓库的 Skill；
- 以 `SKILL.md` 为入口识别的 Skill 目录；
- Skill 目录中的说明、脚本、配置、引用资料、资源文件和依赖文件；
- 计划在公司内部共享或上架到公司 SkillHub 的 Skill；
- 已经在公司 SkillHub 上架并可供员工使用的 Skill。

没有进入本管理流程的本地 Skill、公网下载 Skill 或个人复制的 Skill，不得被称为公司正式可信 Skill，也不得以公司官方名义分发。

## 3. 基本原则

### 3.1 代码入库不等于安全通过

Skill 进入 Gerrit 只说明来源可以找到，不代表内容已经通过安全认可。

### 3.2 检查完整 Skill 内容

`SKILL.md` 用于找到 Skill，但检查范围不能只看 `SKILL.md`，还要覆盖同一 Skill 目录中的脚本、配置、依赖、引用资料和其他相关文件。

### 3.3 安全结论只对明确版本有效

审查必须对应明确的代码版本和内容。Skill 内容变化后，新版本必须重新进入检查流程，不能直接沿用旧版本的“已通过”状态。

如果代码版本不同但 Skill 内容完全相同，可以按公司规则复用仍然有效的检查结果，但每个代码版本的来源记录都必须保留。

### 3.4 产品线对 Skill 负责

产品线是 Skill 的责任主体，负责确认 Skill 用途、负责人、权限需求、数据使用、整改和是否申请上架。

CM、Security 和平台负责管理、检查、审核和提供上架能力，不代替产品线决定是否对外提供该 Skill。

### 3.5 产品线自行上传和确认上架

产品线必须主动确认并完成 Skill 的上传或上架申请。CM 和平台不得把代码库中的 Skill 自动公开上架。

平台可以根据台账为产品线建立“私密候选 Skill”或发送待确认提醒，但候选 Skill 默认不可被普通用户搜索和安装。只有产品线确认、提交上架，并完成检查和审核后，才可以公开发布。

### 3.6 上架版本必须与审查版本一致

SkillHub 中公开的 Skill 必须与审查通过的代码版本和内容一致，不能使用“最新版本”等会自动变化的内容作为上架对象。

### 3.7 上架前检查与上架后管理并重

安全管理不仅包括上架前审查，也包括上架后的变更关注、定期复查、风险告警、下架和恢复。

## 4. 角色和职责

| 角色 | 主要职责 |
|---|---|
| 产品线 / Skill 负责人 | 创建和维护 Skill；确认用途、负责人和使用范围；完成整改；自行上传或申请上架 |
| CM | 维护台账；组织审查；跟踪待办；维护流程状态和记录 |
| Security | 制定检查规则；处理高风险问题；审核有条件通过；参与紧急风险处置 |
| SkillHub 管理员 | 管理平台权限、上架、下架和平台运行，不代替产品线确认 Skill |
| 普通用户 | 只使用公司 SkillHub 中已正式上架的 Skill；发现异常时及时反馈 |

重要操作应尽量由不同角色分别完成，避免同一个人同时修改 Skill、批准审查并完成公开上架。

## 5. Skill 识别和版本

### 5.1 Skill 管理边界

- `SKILL.md` 所在目录视为一个 Skill 的根目录；
- 根目录下与 Skill 一起使用的文件视为一个完整 Skill；
- 根目录内任一受管理文件变化，都视为该 Skill 可能发生变化。

### 5.2 一条 Skill 台账的识别信息

一条 Skill 台账由以下信息共同确定：

```text
代码仓库 + 分支 + Skill 路径 + Skill 名称
```

仓库、分支、路径或名称不一致时，先分别登记。经产品线确认后，可以在管理页面中标记它们属于同一种能力，但不能删除原有来源和历史记录。

### 5.3 两种版本信息

每个 Skill 同时保留：

- **代码版本**：使用 Commit ID，说明 Skill 来自哪次代码提交；
- **内容校验值**：使用完整 Skill 内容计算 SHA-256，说明两份 Skill 内容是否完全一致。

代码版本用于追查来源，内容校验值用于判断内容是否变化、检查结果是否可以复用。公司不使用 MD5 作为 Skill 的安全完整性标识。

## 6. 总体管理流程

![企业内部 Skill 安全管理流程](./diagrams/skill-security-management-flow.png)

整体流程分为六个环节：

```text
代码变化
→ Skill 发现与台账登记
→ 自动检查与人工审查
→ 产品线确认并提交上架
→ SkillHub 发布和使用
→ 持续关注、下架和恢复
```

## 7. Skill 发现和台账登记

### 7.1 新增和变更发现

Gerrit 中出现以下情况时，应更新 Skill 台账：

- 新增 `SKILL.md`；
- 修改 Skill 目录中的文件；
- 删除 Skill 或 `SKILL.md`；
- 移动或重命名 Skill；
- 一次提交同时影响多个 Skill。

新增和日常变更由 Gerrit 服务端钩子发现，不依赖开发人员电脑上的本地设置。

### 7.2 历史 Skill 盘点

历史存量通过全量检查发现。全量检查应找到纳管代码仓库中已经存在的 `SKILL.md`，补齐历史 Skill 台账，并定期核对代码库和台账是否一致。

### 7.3 台账信息

台账至少记录：

- Skill 名称和说明；
- 所属产品线、负责人；
- 代码仓库、分支和目录；
- 当前 Commit ID 和内容校验值；
- 首次发现时间和最近变化时间；
- 当前检查状态；
- 当前上架状态；
- 最近一次审查时间和审查人；
- 风险等级和需要整改的问题；
- 删除、移动、下架和退役记录。

### 7.4 内容变化后的处理

Skill 内容变化后：

1. 保留原版本记录；
2. 登记新版本；
3. 将新版本设为待检查；
4. 上一已通过版本不自动失效；
5. 新版本检查通过前，不得替换 SkillHub 中的上一正式版本。

## 8. 安全检查和人工审查

### 8.1 自动检查

自动检查同时使用常规静态检查工具和 AI 检查能力，从不同角度判断 Skill 风险。自动检查不直接执行不可信 Skill 中的脚本。

检查范围至少包括：

| 检查内容 | 重点关注 |
|---|---|
| 指令内容 | 是否诱导 AI 忽略规则、越权操作或隐藏真实目的 |
| 脚本和命令 | 是否执行危险命令、拼接外部输入或下载后直接运行 |
| 文件操作 | 是否读取、修改或删除不应访问的文件 |
| 网络访问 | 是否连接未知地址、上传数据或从外部下载内容 |
| 账号和密码 | 是否包含密码、令牌、私钥或读取敏感环境变量 |
| 外部工具 | 是否调用未说明或权限过高的工具、MCP 服务 |
| 依赖和安装 | 是否使用不安全来源、已知漏洞或不固定版本 |
| 数据使用 | 是否可能泄露源码、配置、用户数据或公司数据 |
| 说明与行为 | Skill 描述是否与实际行为一致 |
| 特殊文件 | 是否存在无法检查的二进制、压缩包、外部引用等内容 |

自动检查失败、超时、内容无法识别或检查范围不完整时，不能当作检查通过。

### 8.2 风险等级

| 等级 | 含义 | 处理方式 |
|---|---|---|
| 严重 | 明确恶意、凭据窃取、严重数据泄露或破坏行为 | 立即阻断，不得上架 |
| 高 | 很可能造成越权、执行、泄露或供应链问题 | 必须由 Security 复核 |
| 中 | 有一定风险，但可能是业务确实需要的能力 | 产品线说明用途，必要时由 Security 复核 |
| 低 | 影响较小、发生可能性较低 | 满足公司规则时可通过或抽查 |
| 提示 | 主要用于说明和提醒 | 记录并供审查参考 |

综合评分用于帮助排序和判断，不能掩盖严重风险。只要存在尚未处理的严重问题，该版本就不能上架。

### 8.3 人工审查

以下情况必须人工审查：

- 出现严重或高风险；
- 中风险是否合理无法由工具判断；
- Skill 需要访问敏感系统、敏感数据或高权限账号；
- 自动检查没有覆盖全部内容；
- 产品线、CM 或 Security 认为需要进一步确认。

人工审查重点确认：

- Skill 的真实业务用途；
- 所需权限是否必要；
- 文件、网络和数据访问是否合理；
- 风险是否已经修复或可以控制；
- Skill 说明是否与实际行为一致。

### 8.4 审查结果

审查结果分为：

- 通过；
- 拒绝；
- 需要整改；
- 有条件通过。

“有条件通过”必须写明原因、限制措施、批准人和有效期限。期限到期、内容变化或限制措施失效后，应重新审查。

## 9. 产品线确认和 SkillHub 上架

### 9.1 私密候选和提醒

平台可以根据台账：

- 向产品线发送待确认提醒；
- 在 SkillHub 中建立只有相关产品线可见的私密候选记录；
- 展示来源、版本、检查结果和待补充信息。

私密候选不是正式上架，普通用户不得搜索、查看或安装。

### 9.2 产品线自行提交

产品线确认需要共享的 Skill 后，应自行完成：

- 确认负责人和用途；
- 补充功能、权限、数据和网络访问说明；
- 选择需要上架的明确代码版本；
- 处理检查发现的问题；
- 提交上架申请或执行平台规定的上传操作。

CM 和平台可以提醒、协助和校验，但不得代替产品线自动公开上架。

### 9.3 上架条件

Skill 同时满足以下条件后才可公开上架：

- 来源属于公司纳管代码仓库；
- 产品线和负责人明确；
- 上架版本明确；
- 自动检查已经正常完成；
- 必要的人工审查已经完成；
- 没有尚未处理的严重或高风险；
- 有条件通过仍在有效期内；
- 上架内容与审查通过的内容完全一致；
- 产品线已主动确认并提交上架。

### 9.4 上架信息

SkillHub 页面至少展示：

- Skill 名称、功能说明和版本；
- 所属产品线和负责人；
- 来源仓库、分支、路径和 Commit ID；
- 检查状态、风险等级和最近审查时间；
- 所需权限、数据和网络访问说明；
- 发布时间和当前状态。

## 10. 使用、升级和变更

- 普通用户只使用 SkillHub 中正式上架的 Skill；
- 下架 Skill 不再提供新安装；
- Skill 升级只能升级到新的已通过版本；
- Gerrit 中出现新 Commit 时，不得自动升级 SkillHub 或用户已安装版本；
- 新版本检查期间，上一无已知风险的正式版本可以继续使用；
- 产品线应及时维护负责人、说明、权限和依赖信息。

## 11. 持续关注和风险处置

### 11.1 需要重新关注的情况

- 已上架 Skill 出现新版本；
- 检查规则发生重要变化；
- Skill 使用的依赖出现严重漏洞；
- 发现新的恶意地址、恶意文件或供应链问题；
- 上架内容与审查记录不一致；
- Skill 来源被删除或无法访问；
- 有条件通过已经到期；
- 产品线、Security 或用户报告异常行为。

### 11.2 告警和通知

发现安全问题时，应通知产品线负责人、CM 和 Security；需要平台操作时同步通知 SkillHub 管理员。

严重风险应立即处理，普通平台故障和安全风险应分别通知，避免安全问题被一般运维告警淹没。

### 11.3 下架处理

| 情况 | 处理方式 |
|---|---|
| 严重风险或明确恶意行为 | 立即下架或紧急封禁 |
| 高风险 | 停止新安装并复核，根据影响决定是否立即下架 |
| 中风险 | 通知整改，根据业务影响决定是否限制使用 |
| 低风险或提示 | 记录、观察或抽查 |

下架后应：

- 停止新安装；
- 标明下架原因；
- 通知相关产品线和受影响用户；
- 给出停用、替代或升级建议；
- 保留原版本、检查结果和处理记录。

### 11.4 恢复上架

恢复上架必须满足：

- 问题已经修复或风险已经解除；
- 修复内容形成新的明确代码版本；
- 重新完成自动检查和必要的人工审查；
- 重新满足正常上架条件；
- 由产品线重新确认并提交。

不得只修改平台状态来绕过重新审查。

## 12. 状态管理

底层应分别记录检查状态、审查状态和上架状态，不能只保存“已审/未审”。

### 12.1 检查状态

```text
未检查
待检查
检查中
检查完成
检查失败
```

### 12.2 审查状态

```text
未审查
待审查
已通过
已拒绝
需要整改
有条件通过
已失效
```

### 12.3 上架状态

```text
未进入 SkillHub
私密候选
待产品线确认
已上架
已下架
已退役
```

## 13. 记录和追查

以下事项必须保留记录：

- Skill 首次发现和台账登记；
- 新版本、删除、移动和重命名；
- 自动检查结果和发现的问题；
- 人工审查结论；
- 有条件通过的申请、批准和到期；
- 产品线上传和上架确认；
- SkillHub 上架、升级、下架和恢复；
- 风险告警和处理结果；
- 负责人、权限和关键信息变化。

系统应能够清楚回答：

> 某个已上架 Skill 来自哪个产品线、仓库、目录和代码版本，检查过哪些内容，发现过什么问题，由谁确认和审查，何时上架，以及是否发生过下架和恢复。

## 14. 最终管理要求

1. 公司正式 Skill 必须有明确的 Gerrit 来源、产品线和负责人。
2. 安全检查必须覆盖完整 Skill 内容，不能只检查 `SKILL.md`。
3. Skill 内容变化后，新版本必须重新进入检查流程。
4. 自动检查结果不能单独代表最终批准。
5. 检查失败、超时或覆盖不完整时不能视为通过。
6. 严重风险不得上架，高风险必须经过 Security 复核。
7. 上架版本必须与审查通过的代码版本和内容完全一致。
8. 产品线必须主动确认并自行上传或提交上架，CM 和平台不得自动公开上架。
9. 平台建立的私密候选只能用于提醒和确认，不属于正式上架。
10. 新版本未通过前，不得替换上一已通过版本。
11. 下架、恢复和有条件通过都必须保留完整记录。
12. 已上架 Skill 出现新风险时，必须能够告警、限制、下架并重新审查。

---

> 管理原则：来源清楚、责任明确、版本可查、风险经过检查、产品线主动上架、异常能够下架、全过程留有记录。
