## 1. 任务边界

本 WBS 覆盖从 CSV 台账冻结，到仓库下载、Skill 快照、两套静态检查、Claude Code AI 审查、统一结论、质量评分、证据留存、本地私密候选导出和清理的完整链路。

本阶段明确不做以下动作：

- 不执行被审查 Skill 中的脚本、命令、安装程序或 MCP 工具；
- 不把 Skill 内容发送到公网模型、公共云扫描服务或第三方上传服务；
- 不自动修改原 Gerrit 仓库中的 Skill；
- 不自动 Commit、Push 候选 Skill，也不自动上架 SkillHub；
- 不由 CM 或平台替代产品线确认 Skill 是否进入候选或正式共享；
- 不处理 POC 目录中的内容；
- 不因为评分高而放宽安全门禁。

通过审查的内容只导出到本地 `private-candidates/` 工作区。后续是否手动同步到私密 Git 中转仓库，由负责人另行确认。

## 2. WBS 使用规则

### 2.1 任务状态

每个任务只能使用以下状态：

```text
待开始      尚未满足依赖条件
准备中      正在收集输入或配置环境
执行中      正在实现、运行或验证
待人工确认  自动结果已产生，但需要指定人员判断
已完成      验收标准全部通过且证据已留存
阻塞        缺少前置数据、权限或外部决策
失败        已执行但未达到验收标准，需要修正后重试
```

缺少用户提供的内网参数时，任务标记为 `阻塞`，不能用假地址、假版本或默认状态值继续批量运行。

### 2.2 每个任务的完成记录

每个任务完成时至少记录：

```text
task_id
batch_id（如果已经进入批次执行）
operator
started_at
finished_at
input_refs
output_refs
tool_or_rule_version
acceptance_evidence
status
blocker_or_risk（如有）
```

任务输出必须可回查。不能只在聊天记录、终端临时输出或人工口头说明中保留结论。

### 2.3 统一安全约束

以下约束适用于所有任务：

- 运行仓库访问只使用专用只读 SSH 身份；不把私钥放进工作区、日志或候选目录；
- 目标 Skill 快照按只读方式处理，扫描过程不安装其依赖；
- Cisco AI Skill Scanner 和 NVIDIA SkillSpector 必须使用本地、静态、无上传的配置；
- AI 审查只允许读取文件，不能使用 Bash、脚本执行、MCP、网络、写文件或子代理；
- 原始报告进入受限证据区，不进入候选工作区；
- 任何 Digest 不一致、报告缺失或检查范围不完整，都不能判定为安全通过；
- 所有事件处理、扫描和结果落盘都必须可以重复执行而不覆盖历史结果。

## 4. 阶段 0：规则、输入和环境准备

### T00 建立批次与规则基线

| 项目 | 内容 |
|---|---|
| 目标 | 在任何仓库下载前固定本批次使用的安全规则、质量规则、状态定义、目录边界和禁止动作，避免同一批次中途换规则。 |
| 输入 | `AGENTS.md`、`docs/11-final-skill-security-management-framework.md`、`docs/13-skill-batch-security-review-and-scoring-design.md`、用户确认的内网环境约束。 |
| 输出 | 批次配置记录；`batch_id` 生成规则；安全规则版本；质量规则版本；候选质量门槛（当前设计为 70）；状态映射；文件大小和超时限制；重试次数；并发上限；证据和候选目录定义。 |
| 依赖 | 无。 |
| 验收标准 | 1. 明确保存 `policy_version`、`quality_policy_version` 和配置版本；2. 安全结论与质量得分分别定义；3. 明确“禁止执行 Skill”和“禁止自动 Push 候选”；4. 所有运行参数都有来源或明确标记为待用户提供；5. 规则冻结后，批次内修改会产生新批次或新版本记录。 |
| 可并行关系 | 完成后 T01、T02、T03、T04、T05、T06 可并行。 |

### T01 CSV 输入契约与样例验收

| 项目 | 内容 |
|---|---|
| 目标 | 确认 CSV 可以稳定读取，并把原始行转换成可追溯的台账记录。 |
| 输入 | 用户提供的正式 CSV；字段 `skill_id`、`skill_name`、`repo_name`、`branch`、`skill_path`、`latest_commitid`、`security_reviewed`、`status`、`update_time`、`history_id`。旧七列格式继续兼容。 |
| 输出 | CSV 输入快照；字段和编码检查报告；逐行 `source_row_id`；规范化记录；重复行、冲突行和无效行清单；`status` 映射表。 |
| 依赖 | T00。 |
| 验收标准 | 1. UTF-8、表头、分隔符和空值处理结果明确；2. 正式十列字段全部识别并保留追溯字段；3. `latest_commitid` 只进入 `inventory_revision`，不冒充最终 `source_revision`，旧 `lasted_commited` 仅兼容；4. `skill_path` 禁止绝对路径、`..` 越界、空字节和未规范化分隔符；5. 重复行不生成重复任务但保留所有来源行；6. 未知 `status` 不按有效状态处理；7. 原始 CSV 不被改写。 |
| 可并行关系 | 可与 T02、T03、T04、T05、T06 并行；完成后是 T10 的前置。 |

| 项目 | 内容 |
|---|---|
| 目标 | 建立 `repo_name` 到唯一 Gerrit SSH 地址的受控映射，并验证批量下载所需的只读权限。 |

| 依赖 | T00。 |
| 验收标准 | 1. 每个 `repo_name` 只能解析到一个允许的 SSH 地址；2. 只读身份可以读取目标分支和 Commit；3. 下载不使用 HTTPS Token 或开发者个人凭据；4. 私钥不写入项目和日志；5. 仓库不存在、权限不足、分支不存在均有明确错误状态；6. 访问测试不会修改远端仓库。 |

### T03 `ref-update` 与台账 Commit 对账

| 项目 | 内容 |
|---|---|
| 目标 | 说明当前 `release/hooks/ref-update` 产生的 `latest_commitid` 如何进入 CSV，并确认它是否代表预期的最新版本。 |
| 输入 | 本地 `release/hooks/ref-update`；当前 release 数据结构；CSV 导出样例；新增、修改、连续提交和删除 Skill 的代表性样本；如可提供则使用对应 Gerrit 提交记录。 |
| 输出 | `latest_commitid → inventory_revision` 映射说明；Hook 参数取值验证记录；台账差异规则；问题和风险清单。 |
| 依赖 | T00；建议同时具备 T01 的 CSV 样例。 |
| 验收标准 | 1. 能证明样本中的 `latest_commitid` 是否对应更新后 Commit；2. 明确 `oldrev`、`newrev` 与当前 Hook 参数的对应关系；3. 发现 Hook 取值不确定时，批量流程仍以冻结的远端分支 HEAD 作为 `source_revision`；4. 不把 Hook 中的凭据或完整敏感值复制到报告；5. 本任务只做对账和记录，不擅自修改生产 Hook。 |
| 可并行关系 | 可与 T01、T02、T04、T05、T06 并行；完成后是 T10 的前置。 |

## 5. 阶段 1：来源冻结、下载和 Skill 快照

### T10 来源对账与跨分支候选选择

| 项目 | 内容 |
|---|---|
| 目标 | 根据 CSV、远端分支和 Skill 路径确定本批次实际审查对象，同时保留所有来源事实。 |
| 输入 | T01 的规范化 CSV；T02 的仓库映射；T03 的对账规则；远端分支和 Commit；Skill 路径选择规则。 |
| 输出 | 冻结的 `batch_manifest`；每行 `source_row_id`；`resolved_branch_head`；`skill_last_change_revision`；`skill_last_change_time`；`source_revision`；选择状态。 |
| 依赖 | T01、T02、T03、T06。 |
| 验收标准 | 1. 来源事实键使用 `repo_name + branch + normalized_skill_path + skill_name`；2. 常规审查分组使用 `repo_name + normalized_skill_path`；3. 按 Skill 路径最近变化时间选最新候选，不比较 SHA 字符串；4. 旧分支保留并标记 `SKIPPED_SUPERSEDED_BRANCH`；5. 同时间且 Digest 不同的版本不静默丢弃，标记 `BRANCH_CONTENT_CONFLICT`；6. Commit、分支、路径不一致时标记 `STALE_INVENTORY` 或 `INPUT_INVALID`；7. 批次冻结后不再从浮动分支名取得内容。 |
| 可并行关系 | 同一批次该任务应在输入验收后集中完成；不同仓库的来源解析可以有限并行。 |

### T11 单仓库只读镜像与下载管理

| 项目 | 内容 |
|---|---|
| 目标 | 同一批次内每个仓库只下载或更新一份只读对象镜像，为多个 Skill 和多个冻结 Revision 提供来源。 |
| 输入 | T10 的仓库和 Revision 清单；T02 的 SSH 映射和只读权限；下载超时、重试和磁盘限制。 |
| 输出 | 仓库级只读镜像或对象缓存；下载日志；远端 HEAD 校验；仓库错误和重试记录。 |
| 依赖 | T10、T02。 |
| 验收标准 | 1. 同一批次同一仓库只建立一份镜像；2. 镜像包含后续所需的冻结 Commit；3. 下载使用 SSH 且不把凭据写入缓存；4. 分支继续变化不会改变已冻结内容；5. 临时网络失败可按策略重试，权限、仓库不存在和 Commit 不存在不能伪装为临时失败；6. 下载阶段不执行仓库中的脚本、构建和安装动作。 |

| 输出 | 批次总览；Skill 明细；失败和待确认清单；质量分布；候选清单；独立结果 CSV/JSON；台账差异报告。 |
| 依赖 | 当前批次任务完成或已进入明确失败/待人工终态；T40、T42。 |
| 验收标准 | 1. 总览包含仓库数、来源行数、选中内容版本数、旧分支数、冲突数、台账差异数、四类安全结论数量、质量等级分布、候选数和失败数；2. 明细包含来源、Commit、Digest、两套静态工具、AI、统一安全结论、质量分、人工原因和候选状态；3. 原始 CSV 不被直接覆盖；4. 独立结果至少包含审查批次、实际审查 Revision、Digest、安全结论、质量分、策略版本、时间和候选状态；5. `security_reviewed` 不被解释成安全通过。 |
| 可并行关系 | 可以在各仓库完成后持续生成局部汇总；最终总览需等待所有仓库终态。 |

### T51 小批量端到端验收

| 项目 | 内容 |
|---|---|
| 目标 | 用少量真实仓库和可控测试样本验证整条链路，再决定是否处理 100 多个仓库和数百个 Skill。 |
| 输入 | T00 至 T50 的实现；用户指定的小批量仓库和 Skill；覆盖正常、重复、跨分支、台账过期、工具失败、Digest 不一致、特殊文件和风险问题的测试数据。 |
| 输出 | 小批量验收报告；问题修复清单；参数调整记录；是否进入全量批次的负责人确认。 |
| 依赖 | T50；所有必须的内网参数已经提供。 |
| 验收标准 | 1. 能回查每一行 CSV 到来源、快照、工具报告、AI 结果和最终结论；2. 同仓库只下载一次；3. 同时间不同内容的分支不会被静默丢弃；4. 两套静态工具并行且 AI 不早于静态结果；5. 目标 Skill 未被执行；6. 失败可重试、可断点继续且不会错误复用结果；7. 候选只落在本地，不发生 Commit、Push 或上架；8. 清理后证据和候选仍完整；9. 负责人书面确认可进入全量。 |
| 可并行关系 | 验收期间可并行修复不相互影响的适配问题，但每次修复后必须重新跑受影响的验收用例。 |

### T52 全量批次执行

| 项目 | 内容 |
|---|---|
| 目标 | 在小批量验收通过后，按冻结配置处理 100 多个仓库和数百个 Skill，生成完整审查和候选结果。 |
| 输入 | T51 的通过报告；正式 CSV；完整仓库映射和 SSH 访问；冻结的工具、AI、规则和资源配置。 |
| 输出 | 全量批次证据、统一结果、人工待办、本地候选、失败重试清单和批次报告。 |
| 依赖 | T51；所有必要的用户参数和权限已确认。 |
| 验收标准 | 1. 每个 CSV 来源行都有终态或明确的失败/待人工状态；2. 每个选中 Skill 绑定实际冻结 Commit 和 Digest；3. 仓库按队列处理，单仓库失败不阻塞其他仓库；4. 并发、重试、时间和磁盘限制生效；5. 不执行被审查 Skill、不访问公网、不自动 Push 候选；6. 原始证据和候选目录隔离；7. 能从中断处恢复；8. 汇总数量与明细逐项一致。 |
| 可并行关系 | 不同仓库可有限并行；单仓库内下载、快照、静态检查、AI、结论和清理遵守依赖关系。 |

### T53 候选交接清单（仅交接，不自动同步）

| 项目 | 内容 |
|---|---|
| 目标 | 为负责人后续手动同步到私密 Git 中转仓库提供清晰的候选清单和版本核对依据。 |
| 输入 | T50、T52 的候选目录、脱敏摘要、来源 Manifest、Digest 和人工确认记录。 |
| 输出 | 候选交接清单；每个候选的仓库、Skill 路径、来源 Commit、Digest、质量分、安全结论和证据索引；手动同步检查项。 |
| 依赖 | T50 或 T52；候选必须已通过 T41 和 T42。 |
| 验收标准 | 1. 清单只列出符合候选条件的 Skill；2. 每个候选可由 Digest 和来源 Commit 回查；3. 清单不包含原始报告和完整敏感信息；4. 文档明确由产品线/负责人手动确认和同步；5. 本任务不执行 Git Commit、Push、发布或平台上架。 |
| 可并行关系 | 可与批次报告并行生成；不与任何自动同步动作绑定。 |

## 11. 推荐的逐项执行顺序

### 11.1 首次实现顺序

```text
1.  完成 T00，冻结规则和目录边界
2.  并行完成 T01、T02、T03、T04、T05、T06
3.  完成 T10，生成批次清单和跨分支选择结果
4.  完成 T11、T12，验证单仓库下载、独立快照和 Digest
5.  完成 T13，验证幂等键和结果复用
6.  并行实现并验证 T20、T21，再完成 T22
7.  完成 T30，生成一个 Skill 的 AI 输入包
8.  由负责人通过 Claude Code 执行 T31，完成 T32
9.  完成 T33、T34，并对一条待确认记录执行 T35
10. 完成 T40、T41、T42，确认候选只写本地且不 Push
11. 完成 T50，核对报告数量和明细
12. 用 T51 做小批量端到端验收
13. T51 通过后再执行 T52 全量批次
14. 最后生成 T53 交接清单，由负责人手动处理后续同步
```

### 11.2 单仓库执行顺序

```text
冻结仓库对象
  → 导出各 Skill 快照
  → 生成 Manifest 和 Digest
  → Cisco 与 SkillSpector 并行静态检查
  → 校验静态报告
  → 生成 AI 任务
  → 负责人用 Claude Code 执行 AI 审查
  → 校验 AI 结果
  → 统一问题、结论和质量评分
  → 人工确认（如需要）
  → 保存证据
  → 导出合格的本地候选
  → 复核 Digest 和结果
  → 清理当前仓库临时空间
```

如果某个 Skill 发生 `BLOCKED`、`REVIEW_REQUIRED` 或 `INCOMPLETE`，不影响同一仓库其他 Skill 继续，但当前仓库在清理前必须为该 Skill 保存失败或待人工记录。只有候选、证据和恢复信息全部落盘后，才能删除仓库临时目录。

## 12. 任务验收总门槛

只有同时满足以下条件，才能认为首轮批量审查实施完成：

1. 所有输入行可以回查，且来源、分支、路径和实际审查 Commit 明确；
2. 同一仓库只下载一次，同一 Skill 快照不会因浮动分支变化而改变；
3. Digest 覆盖完整 Skill Package，工具和 AI 使用同一 Digest；
4. Cisco 和 SkillSpector 都完成静态检查，或明确记录失败/未覆盖；
5. AI 审查只使用公司内网模型和只读权限，未执行目标 Skill；
6. 安全结论与质量评分分离，任何未完成或高风险问题都不会自动通过；
7. 原始报告、统一结果、人工决策和事件日志都进入受限证据区；
8. 候选区只包含满足安全和质量门槛的内容，且没有原始报告；
9. 当前阶段没有自动 Commit、Push 或 SkillHub 上架动作；
10. 断点继续、重试、失败隔离和工作区清理经过测试；
11. 小批量验收通过后，才允许扩大到全量仓库和 Skill；
12. 全量报告的总数、明细和候选清单相互一致。

## 13. 不纳入本阶段执行的事项

以下事项保留在后续治理或平台建设范围，不作为本 WBS 的完成条件：

- 产品线是否确认正式共享 Skill；
- 私密候选 Git 中转仓库的人工全量同步；
- SkillHub 正式上架、搜索、安装和权限控制；
- Gerrit 增量 Hook/Event 接入和定时 reconciliation；
- 自动整改或自动修改原仓库 Skill；
- Agent Runtime 强制可信源；
- 公网 SkillHub 或外部 Skill 引入审批；
- 实际业务效果测试和受控执行环境评测。
